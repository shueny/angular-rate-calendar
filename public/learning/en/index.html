Library→Framework

Switch mindsets first: library vs. framework

React only handles the view; every other layer is a package you pick yourself. Angular ships routing, forms, HTTP, dependency injection, testing utilities, and a CLI in the box. Angular feels like "a lot" not because it's harder, but because choices that are spread across the React ecosystem land in front of you all at once.

The cost is less flexibility. The payoff is that Angular projects all look alike, so switching teams or inheriting an old codebase is cheap.

What exactly is "a lot"?

I listed every Angular concept I ran into in the first week of building Rate Calendar and couldn't route around: 13 of them. The same feature in React gets moving with 4 core concepts in week one: JSX, props, useState, and useEffect. You still need routing, forms, data fetching, and testing eventually, but you can pick those packages and learn them when you actually need them.

So React's learning cost isn't smaller; it's spread out later, and you have to make the choices. Angular's is front-loaded, but already decided for you.

useState / useMemo→signal / computed

Signals: recompute only what's actually affected

In React, when state changes, the component that owns it and every child re-run by default, and you opt out by hand with memo and useMemo. Angular signals remember who read what, forming a dependency graph; when a value changes, only the computed() values and templates that read it update.

On the left is Rate Calendar's actual dependency graph; on the right is the component tree for the same feature written in React. Try the controls, especially "Pick another day".

React

const [config, setConfig] = useState(DEFAULT);
const rules = useMemo(
  () => buildRules(config), [config]
);   // you must get the deps array right

Angular · pricing-engine.service.ts

private readonly _config = signal(DEFAULT_PRICING_CONFIG);
readonly rules = computed(() => {
  const c = this._config(); // reading subscribes
  return [new WeekendRule(c.weekendMultiplier), …];
});
Context + useContext→Injector + inject()

Dependency injection: walk up until you find it

React has no built-in DI; the closest thing is Context: create a context, wrap a Provider higher up, call useContext lower down. Angular makes this part of the framework core. A component calls inject(X), and Angular starts at that component's injector and walks up, using the instance from the first level that provides X.

The level where it's found decides the instance's lifetime and who shares it, which is also why swapping in a mock for tests is easy.

React

const EngineCtx = createContext<Engine | null>(null);

<EngineCtx.Provider value={engine}>
  <ConfigForm />
</EngineCtx.Provider>

const engine = useContext(EngineCtx);

      plugin array→PricingRule interface
      
The pricing engine: what the Strategy pattern looks like

    

    

      
Every rule implements the same PricingRule interface. The engine only sorts rules by order, drops disabled ones, and multiplies their factors in turn. Adding a rule means writing one more class; the calendar, the form, and the other rules don't change.

      
Click any day to watch its price flow through the three rules. The numbers are the project's defaults: base rate $100, weekend ×1.25, public holiday ×1.5, peak season (June, July, August, December) ×1.2.

    

    
    

      

        
pricing-rule.model.ts


export interface PricingRule {
  name: string;
  order: number;
  enabled: boolean;
  apply(ctx: PricingContext): PriceAdjustment | null;
}

      

      

        
pricing-engine.service.ts · calculate()


const adjustments = this.rules()
  .filter((rule) => rule.enabled)
  .map((rule) => rule.apply(context))
  .filter((adj) => adj !== null);

const finalRate = adjustments.reduce(
  (rate, adj) => rate * adj.multiplier, baseRate);

      

    

  


  
  

    

      JSX→Template
      
Template syntax side by side

    

    

      
JSX is "markup inside JavaScript"; an Angular template is "bindings added to HTML". Three kinds of brackets cover most templates: [property] passes data down, (event) sends events up, and {{ }} interpolates. Since Angular 17, @if and @for replace the old *ngIf and *ngFor; new projects can learn only the new syntax.

      Error message→Lesson learned
      
Pitfalls I hit

    

    
Real problems from this project, each with the error I saw, the cause, and the fix.

    

      
Environment

        
The latest Angular CLI wouldn't install

        Node.js v22.22.2 — @angular/cli requires ≥ 22.22.3
        
Fix: used npx @angular/cli@19 new to pin the major version to 19.

        
Lesson: the Angular CLI has a strict Node version range; document it in the README.

      

      
Unit tests

        
Vitest couldn't run Angular components

        ERR_MODULE_NOT_FOUND — @analogjs/vitest-angular × vitest@5
        
Fix: switched to @analogjs/vite-plugin-angular and wrote my own test-setup.ts that loads zone.js and initializes the TestBed environment.

        
Lesson: a React component is a plain function you can just render; an Angular component needs TestBed and a compile environment set up first.

      

      
E2E

        
Playwright couldn't find a browser

        Executable doesn't exist — expected chromium revision 1243, installed 1194
        
Fix: pointed executablePath at the installed Chromium locally; CI runs playwright install as usual.

        
Lesson: each Playwright version is pinned to one Chromium revision.

      

      
Lint

        
ESLint rejected constructor injection

        @angular-eslint/prefer-inject
        
Fix: changed constructor(private http: HttpClient) to private http = inject(HttpClient).

        
Lesson: modern Angular prefers inject(). It reads a lot like a React hook and fits standalone components better.

      

      
Lint

        
An empty ngOnInit

        @angular-eslint/no-empty-lifecycle-method
        
Fix: deleted the empty lifecycle method and loaded holidays with an effect() that follows the month signal.

        
Lesson: with signals, much of what used to live in ngOnInit becomes a declarative effect.

      

      
E2E

        
The month-navigation test always failed

        expect(received).not.toBe(expected) — Expected: not "September 2026"
        
Fix: the test went forward one month and back two, so the assertion could never line up. Rewrote it as "forward → check it changed → back → check it's the original month".

        
Lesson: E2E assertions should follow what a real user actually does.

      

      
CI

        
All green locally, red in CI

        MISSING DEPENDENCY — Cannot find dependency '@vitest/coverage-v8'
        
Fix: added @vitest/coverage-v8 to devDependencies. The first install pulled 5.x, which against vitest 4.x failed with coverageFilesDirectory is required and reported 0% coverage; pinning it to vitest's version (4.1.11) produced the real 93.75%.

        
Lesson: CI is a clean environment, and plugin versions must match the host package. "It ran" doesn't mean "it measured".

      

      
Data flow

        
Switching country let old data overwrite new

        Switch to TW before the US request returns → the late US response lands, showing US holidays with TW selected
        
Fix: the service remembers the key of the latest request and only writes the latest response into the signal; stale responses still go into the cache. Also added a 10-second timeout, and a country change now lets the calendar's effect() reload the year on screen.

        
Lesson: signals make state easy to read, but you still own the order async responses arrive in. All three bugs surfaced only after I wrote failing tests first.

      

      
Deploy

        
The build passed, the deploy was rejected

        Branch "main" is not allowed to deploy to github-pages due to environment protection rules.
        
Fix: when Pages was enabled, GitHub created a github-pages environment that only allowed the default branch at the time. Changed the repo's default branch to main and set the environment's deployment rule to main.

        
Lesson: whether you can deploy is repo configuration, not code. When a workflow fails, check whether it was the build step or the deploy step.

      

      
Git

        
The PR wouldn't open

        The branch has no history in common with main
        
Fix: the repo started with only a feature branch, and the main created later shared no ancestor with it; git merge --allow-unrelated-histories created a common history.

        
Lesson: give a new repo an initial commit on main first, then branch from it.

      

    


    
Common traps for React developers

    

      
Following old NgModule tutorialsAngular 19 defaults to standalone components, but many tutorials online are still from the NgModule era.

      
Reaching for RxJS everywhereSignals are enough for simple state; save RxJS for async flows that need cancelling, combining, or throttling.

      
Putting logic in templatesDerive values with computed() in the class; the template should only bind.

      
Treating effect() like useEffectUse it to sync with the outside world (APIs, the DOM); derived data belongs in computed().

      
Ignoring change detection strategyPair signals with OnPush to get the performance benefit of fine-grained updates.

      Rule engine→Pricing copilot
      
Next: a pricing copilot for revenue managers

    

    
This is the side project's next idea. It isn't built yet, and it's based on my assumptions about this kind of product. If it became a real product, the first step would be confirming with the people who actually set prices that this is where the pain is.

    

      
Revenue managers decide daily whether to adjust rates based on holidays, seasonality, and booking pace. The information is scattered, each change takes time, and it's hard to know the impact before you make it.

      
What I want isn't an AI that changes prices on its own, but a copilot: first it looks things up, explains, and simulates; autonomy grows only as accuracy and trust are proven. This project's pricing engine is the foundation. The calendar and the agent use the same rules, so their numbers always agree.

    


    

    
Three design principles

    

      
Every price is explainable
Every answer says which rules applied and with what multipliers. The engine already returns a per-rule list of adjustments; the agent just puts it into words.

      
Write access is enforced by architecture
The agent's tools come in three tiers (read, simulate, propose), with no tool that writes directly. The change is applied by the manager's "Approve" button, not by a prompt telling the model to behave.

      
Autonomy is earned with data
Before moving up a level, show that the previous level's suggestions were accurate and actually adopted. If the data is bad, fix the problems instead of adding features.

    


    
If it became a real product: 30 / 60 / 90 days

    

      
30
Listen and observe
  • Talk in depth with revenue managers, support, and sales
  • Watch one full rate-change workflow end to end
  • Find the single step that takes the most time or fails most often
  • Learn the current data quality and APIs

      
60
Minimum viable version
  • Only levels 1 and 2: Q&A and simulation, no writes
  • Recruit 2–3 managers willing to try it
  • Build an eval: measure answer and calculation accuracy on real questions

      
90
Let the data decide
  • Review time saved, adoption rate, and error rate
  • Move to level 3 (propose + approve) only if the metrics hold
  • If not, fix the problems instead of adding features
