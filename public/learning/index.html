先換腦袋：函式庫 vs 框架

React 只負責畫面，其他每一層都要自己挑套件；Angular 則把路由、表單、HTTP、依賴注入、測試工具和 CLI 全部內建。學 Angular 覺得「東西很多」，不是因為難，而是因為這些原本分散在 React 生態系裡的選擇，一次全部擺到你面前。

代價是彈性比較小；好處是每個 Angular 專案長得都差不多，換團隊或接手舊專案的成本很低。

「東西比較多」到底多在哪

我把做出 Rate Calendar 時第一週就碰到、而且繞不過去的 Angular 概念一個個列出來，共 13 個。同樣的功能用 React 寫，第一週只需要 JSX、props、useState、useEffect 這 4 個核心概念就能動起來。路由、表單、資料抓取、測試當然也要學，但可以等真的用到時再挑套件、再學。

所以 React 的學習成本不是比較少，而是分散在後面，而且要自己做選擇；Angular 則是集中在前面，但不用選。

Angular 概念為什麼第一週就躲不掉React 的對應在專案哪裡出現
元件裝飾器@Component每個元件都要寫 selector、imports、template、style 等設定，不能只寫一個函式。一般函式就是元件rate-calendar.component.ts

元件的 imports 陣列imports: [ ... ]模板用到的元件、指令都要在這裡登記，漏了會報「is not a known element」。檔案頂端 import 就好pricing-config-form（ReactiveFormsModule）
依賴注入@Injectable · inject()光是要打 API 取得 HttpClient，就得用 DI。還要懂 providedIn: 'root' 是什麼意思。不需要，用 import 或 Contextholiday.service.ts

useState / useMemo→signal / computed

Signals：只重算真正受影響的地方

在 React 裡，state 一變，擁有它的元件和底下所有子元件預設都會重新執行，要靠 memo、useMemo 手動擋掉。Angular 的 Signals 會記住「誰讀了誰」，形成一張依賴圖；值改變時只有讀到它的 computed() 和模板會更新。

下面左邊是 Rate Calendar 實際的依賴關係，右邊是同樣功能用 React 寫時的元件樹。試著操作看看，特別是「選另一天」。

const [config, setConfig] = useState(DEFAULT);

Context + useContext→Injector + inject()

依賴注入：往上找，直到找到為止

React 沒有內建 DI，最接近的是 Context：建立 Context、在上層包 Provider、在下層 useContext。Angular 把這件事做成框架核心：元件呼叫 inject(X)，Angular 會從自己的 injector 開始往上找，找到第一個提供 X 的地方就用它的實例。

找到的層級決定了實例的生命週期與共享範圍，這也是測試時可以輕鬆換成 mock 的原因。

定價引擎：Strategy Pattern 的實際樣子

    

    

      
每條規則都實作同一個 PricingRule 介面，引擎只負責依 order 排序、過濾停用的規則，再把倍率依序乘上去。新增規則只需要多寫一個 class，日曆、表單和其他規則都不用改。

      
點日曆上任一天，看那一天的價格如何流過三條規則。數字是專案的預設值：基本房價 $100、週末 ×1.25、國定假日 ×1.5、旺季（6、7、8、12 月）×1.2。

      JSX→Template
      
模板語法對照

    

    

      
JSX 是「在 JavaScript 裡寫標記」，Angular 模板則是「在 HTML 裡加上綁定」。記住三種括號就能讀懂大部分模板：[屬性] 是資料往下傳，(事件) 是事件往上傳，{{ }} 是插值。Angular 17 之後的 @if、@for 取代了舊的 *ngIf、*ngFor，新專案直接學新語法即可。

      錯誤訊息→學到的事
      
踩坑紀錄

    

    
做這個專案時真正遇到的問題。每一個都附上當時的錯誤、原因和最後的解法。

    

      
環境

        
最新版 Angular CLI 裝不起來

        Node.js v22.22.2 — @angular/cli requires ≥ 22.22.3
        
解法：改用 npx @angular/cli@19 new，把大版本鎖在 19。

        
學到：Angular CLI 對 Node 版本有嚴格範圍，專案要在 README 註明版本。

      

      
單元測試

        
Vitest 跑不起 Angular 元件

        ERR_MODULE_NOT_FOUND — @analogjs/vitest-angular × vitest@5
        
解法：改用 @analogjs/vite-plugin-angular，自己寫 test-setup.ts 載入 zone.js 並初始化 TestBed 環境。

        
學到：React 元件是純函式，直接 render 就能測；Angular 元件需要先初始化 TestBed 和編譯環境才能測。

      

      
E2E

        
Playwright 找不到瀏覽器

        Executable doesn't exist — expected chromium revision 1243, installed 1194
        
解法：本機用 executablePath 指向已安裝的 Chromium；CI 則正常執行 playwright install。

        
學到：Playwright 版本和 Chromium revision 是一對一綁定的。

      

      
Lint

        
constructor 注入被 ESLint 擋下

        @angular-eslint/prefer-inject
        
解法：constructor(private http: HttpClient) 改成 private http = inject(HttpClient)。

        
學到：新版 Angular 慣用 inject()，寫起來和 React hooks 很像，也更好搭配 standalone。

      

      
Lint

        
空的 ngOnInit

        @angular-eslint/no-empty-lifecycle-method
        
解法：刪掉空的生命週期方法，假日資料的載入改用 effect() 跟著月份 signal 自動觸發。

        
學到：有了 Signals，很多原本寫在 ngOnInit 的邏輯可以變成宣告式的 effect。

      

      
E2E

        
月份切換測試永遠失敗

        expect(received).not.toBe(expected) — Expected: not "September 2026"
        
解法：原本的測試前進 1 個月再後退 2 個月，斷言根本對不上。改成「前進 → 確認不同 → 後退 → 確認回到原月份」。

        
學到：E2E 斷言要照著使用者真正的操作流程寫。

      

      
CI

        
本機測試全過，CI 卻失敗

        MISSING DEPENDENCY — Cannot find dependency '@vitest/coverage-v8'
        
解法：把 @vitest/coverage-v8 加進 devDependencies。第一次裝到了 5.x，搭配 vitest 4.x 直接報 coverageFilesDirectory is required，coverage 一直顯示 0%；改成和 vitest 同版本（4.1.11）後才得到真實的 93.75%。

        
學到：CI 是完全乾淨的環境；外掛套件的版本要和主套件對齊，不然「有跑」不代表「有算」。

      

      
資料流

        
切換國家時，舊資料蓋掉新資料

        US 請求還沒回來就切到 TW → US 回應晚到，畫面顯示 US 假日但選單是 TW
        
解法：Service 記住「最新一次請求」的 key，只有最新的回應才寫進 signal；舊回應仍放進快取。另外加上 10 秒 timeout，換國家時也改由日曆的 effect() 重新載入「畫面上那一年」。

        
學到：Signals 讓狀態好讀，但非同步回來的順序還是要自己處理。這三個 bug 都是先寫出會失敗的測試，才找到的。

      

      
部署

        
建置成功，部署卻被拒絕

        Branch "main" is not allowed to deploy to github-pages due to environment protection rules.
        
解法：開啟 Pages 時，GitHub 自動建立的 github-pages 環境只允許當時的預設分支部署。把 repo 預設分支改成 main，並把環境的部署規則改成 main。

        
學到：能不能部署是 repo 設定的一部分，不在程式碼裡；看 workflow 失敗時要分清楚是 build 還是 deploy 那一步。

      

      
Git

        
PR 開不起來

        The branch has no history in common with main
        
解法：repo 原本只有 feature branch，後來建立的 main 沒有共同祖先；用 git merge --allow-unrelated-histories 建立共同歷史。

        
學到：新 repo 應該先在 main 放一個初始 commit，再從它開分支。

      

    


    
React 開發者常見的誤區

    

      
照著舊教學寫 NgModuleAngular 19 預設 standalone，網路上很多教學還停在 NgModule 時代。

      
什麼都用 RxJS簡單狀態用 Signals 就好，RxJS 留給需要取消、合併、節流的非同步流程。

      
在模板裡寫邏輯該算的值用 computed() 在 class 裡算好，模板只負責綁定。

      
把 effect() 當 useEffect 濫用用來同步外部世界（API、DOM）；衍生資料應該用 computed()。

      
忽略變更偵測策略搭配 Signals 使用 OnPush，才能拿到精準更新的效能好處。

      規則引擎→房價副駕駛
      
下一步：營收經理的房價副駕駛

    

    
這是這個 side project 的下一步構想，還沒有實作，內容也是我對這類產品的假設。如果真的要做成產品，第一件事是和實際調價的人一起確認痛點是否真的在這裡。

    

      
營收經理每天要看假日、淡旺季和訂房狀況來決定要不要調價。資訊分散，調一次價很花時間，而且調了之後會有什麼影響，當下很難知道。

      
我想做的不是一個會自己改價格的 AI，而是一個副駕駛：先幫忙查詢、解釋和模擬，等準確度和信任都建立起來，再一步步放權。這個專案的定價引擎就是它的地基，同一套規則可以同時給日曆和 Agent 使用，算出來的數字一定一致。

    


    

    
三個設計原則

    

      
每個價格都能解釋
回答一定附上套用了哪些規則、倍率各是多少。定價引擎本來就會回傳逐條的 adjustments，Agent 只是把它說成人話。

      
寫入權限由架構控制
Agent 的工具分成唯讀、模擬、提案三層，沒有直接寫入的工具。真正套用設定的是經理按下的「核准」按鈕，不是靠 prompt 約束。

      
放權要有數據支撐
每進到下一個階段，都要先證明上一階段的建議準確、而且真的有被採納。數據不好就回頭修，而不是繼續加功能。
